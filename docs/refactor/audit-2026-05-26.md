## P0-1. `c107763` 静默修改了 `data/segments.csv`，但 commit 信息与
所有文档都没承认这一点

事实：
- commit 信息：`Harden LLM segment cleanup prompts and audits`

  **207 行** (按 `csv.DictReader` 计；`wc -l` 因为引号内 embedded
  newline 会多报 12 行)。
- 进一步分解：~**17 行** 是 “same zh, different ko” 的 ko-rewrite，~**207
  行** 是纯删除。`segments.csv` SHA256 (大写、与 `training.py::hash_file`
  一致) =
  `D299B01FF90D571CAEA65C6933C1769D3B93B1E04798EEDF2B395C2248482419`。
- 抽样确认是真正的 Korean rewrite，不只是 CRLF/排序漂移。例：
  - `segment_id=327` 韩文从 `{0} {1}를 지불해 상점 목록을 새로고침
    하시겠습니까?` 改为 `{0} {1}을(를) 사용해 {2} 1개를 구매하여 상점
    상품을 새로고침하시겠습니까?` (修正了之前丢失的 `{2}` 占位符，符合
    LLM segment rewrite 期望的行为)
  - `segment_id=352` 也是 ko 改写

但是：

- RF-015 状态写 `BLOCKED`，备注是 `The real full-corpus LLM run is

## P1-1. `scripts/segments_llm_cleanup_pipeline.py` 反向依赖
`scripts/glossary_llm_cleanup_pipeline.py`

事实：

```text
scripts/segments_llm_cleanup_pipeline.py:24:
    from glossary_llm_cleanup_pipeline import (
        ClientConfig,
        call_chat_completion,
        parse_json_content,
        resolve_client_config,
    )
```

分析：
- LLM HTTP 客户端 / 重试 / JSON 解析逻辑应该是 LLM cleanup 这类脚本的
  共享基础，但现在 segments 脚本把它从 glossary 脚本里 import。
- 这违反了 AGENTS.md `Code Style` 的 “Keep pure transformation logic
  in importable modules and keep CLI scripts thin” —— CLI 脚本之间互相
  import，等于把一个 CLI 当库用。
- 任何对 glossary LLM 脚本的改动都可能静默打破 segments LLM 脚本，反之
  亦然。

建议：
- 新建 `scripts/llm_common.py`（或 `src/longtu_translation_pipeline/
  llm_client.py`，更彻底但要做包内 API），把以下四个迁移过去：
  `ClientConfig`, `resolve_client_config`, `call_chat_completion`,
  `parse_json_content`。
- 两个 LLM 脚本都从 `llm_common.py` import，并加单测。
- 这个改动不应该和 LLM 真实运行混在一个 commit。

## P1-3. `configs/training/default.json` 不能用于真正的 `--train`，
但名字叫 `default`

事实：
- `default.json` 里 `training` section 只写了 `num_train_epochs=3` 和
  `per_device_*_batch_size`，没有 `max_steps`。
- `run_real_nllb_formal_training` (RF-006-P9 决策) 要求 `max_steps`
  必须由 config 或 CLI 提供。
- 所以 `--train --config configs/training/default.json` 会立即报错。
- 但脚本的 `--config` 默认值就是 `configs/training/default.json`，初次
  使用者很容易踩坑。

建议：
- 至少在 `default.json` 加一条 `"_comment": "Dry-run / smoke only;
  use full_10k.json for --train"` (不会被 loader 拒绝，因为
  `load_training_arguments_config` 只 require 自己关心的 key)；或者
- 拆成 `configs/training/dryrun_default.json` + `configs/training/
  default_train.json`，并把 `--train` 默认值改成 `full_10k.json`。

## P2-2. `src/longtu_translation_pipeline/__init__.py` 的公开表面与
`scripts/train_model.py` 实际依赖不一致

事实：
- `__init__.py` 导出了 `run_real_nllb_pilot_training`,
  `run_real_nllb_model_smoke_test`, `run_nllb_trainer_smoke_test`，但
  **没有** 导出 `run_real_nllb_formal_training` 和
  `format_formal_training_run`。
- `scripts/train_model.py` 第 12-25 行直接从子模块 import：
  ```
  from longtu_translation_pipeline.training import (
      ...
      run_real_nllb_formal_training,
      ...
  )
  ```

分析：
- 公开 API 和实际入口不一致。要么 `run_real_nllb_formal_training` 也
  应该在 `__init__.py` 暴露 (它是真正的训练入口，比 pilot 更重要)，
  要么 pilot/smoke 入口都不应该在 `__init__.py` 暴露 (因为它们其实只
  是 RF-006 phase 内部的脚本支持函数)。

建议：
- 选择 “只暴露稳定 API” 的方向：把 pilot / smoke / formal 一律从
  `__init__.py` 拿掉，留 `TrainingConfig`, `InferenceConfig`,
  `EvaluationConfig`, `evaluate_translation`, `compute_corpus_bleu`,
  `compute_glossary_preservation`, `protect_training_pair`,
  `strip_glossary_markers` 这类真正稳定的东西。CLI 脚本继续从子模块
  import，这是 CLI 自己的私事。
